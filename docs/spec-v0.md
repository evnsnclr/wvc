# wvc spec v0 (draft, 2026-11-02)

Status: a draft for discussion. Implemented: section 1 (manifests, including the gguf-hash export), section 2 (diff records), `verify` from section 4, and section 5.5 (Hub checkpoints) in `src/wvc/`, plus the conformance vectors of section 7 in `spec/`. Everything else is proposed unless a section says otherwise. Invariant: a checkout reproduces bytes exactly; a reader that cannot must say so.

## 1. Tensor identity and manifests (implemented)
- A tensor blob is the raw stored bytes of one tensor in a safetensors file (little-endian, row-major, as laid out in the file). Its id is `sha256(bytes)`, lowercase hex.
- A manifest describes one checkpoint:
  `{"format": "wvc-manifest/0", "root": <hex>, "tensor_count": n, "total_bytes": b, "tensors": {name: {"dtype", "shape": [...], "nbytes", "sha256"}}}` with tensors sorted by name.
- `root = sha256(concatenation, over names sorted bytewise, of "<escaped name>\t<dtype>\t<shape joined by x>\t<sha256>\n")`, where the escaped name replaces backslash, tab, newline, and carriage return by `\\`, `\t`, `\n`, and `\r`, so a line can never be forged by a name that contains separators; names with control characters (code points below 32 and 127) are refused by the reader anyway, and the manifest validator refuses them too. For names without backslashes the escaping changes nothing.
- Sharding, header order, `__metadata__`, and file names do not affect the root. dtype and shape do. Recognised dtypes: BOOL, U8, I8, F8_E4M3, F8_E5M2, F8_E4M3FNUZ, F8_E5M2FNUZ, F8_E8M0, I16, U16, F16, BF16, I32, U32, F32, I64, U64, F64, C64; identity needs only the byte size, and C64 cannot be decoded to numbers.
- Bounds (fixed 2026-11-03): a shape in a header or a manifest has at most 64 dimensions, each a non-negative integer, and its element count may not exceed the data buffer's (header) or `nbytes`'s (manifest) byte count; a header holding more `{` and `[` bytes than `header_size // 16 + 64`, counted anywhere including inside names, is refused before it is parsed, as is a tensor entry with a value that is not a string or a list of integers. Checkpoint files, manifests (at most 256 MiB), and adapter configs (at most 1 MiB) must be regular files or symlinks to them; a FIFO or a device is refused.
- Header parsing (fixed 2026-11-03, second-pass review P-M7): one parser reads every safetensors header, whether a command reads it from a checkpoint file (`hash`, `diff`, `verify`, `commit`, Hub range reads) or from a stored header payload (3.3: `commit` re-reading what it stored, and every check of a commit's manifest against its file records, as in `show`, `checkout`, `fsck`, and on received commits). The header must be strict JSON: a duplicate key and the constants `NaN`, `Infinity`, and `-Infinity` are refused, as the reference loader refuses them, and tensor names follow the control-character rule above in both places. Every value a header may hold is a string or a list of integers, so no header `hash` accepted before is refused now; only the message is earlier. A stored header payload must also carry a size field that gives its exact length.
- Interoperability: per-tensor ids equal the SHA-256 values people already publish for raw tensor bytes (verified in E001).
- Output bytes (fixed 2026-11-03): `wvc hash` prints the manifest as UTF-8 bytes with LF line endings on every platform, written past the text layer of standard output, so a redirected manifest is byte-identical to the stored `.wvc/manifests/<root>.json`. gguf-hash lines, every `--json` output, and `wvc card` are written the same way, as is the root line of `wvc hash --root-only` (64 hex characters and LF). Human-readable messages keep the console's encoding, with characters it cannot encode escaped rather than raised.
- Export (implemented 2026-11-03): `wvc hash --format gguf-hash` writes llama.cpp gguf-hash manifest lines: per file in name order, `sha256    <hex>  <file>:<tensor>` for each tensor in the order its bytes sit in the file, then `sha256    <hex>  <file>` over the file's tensor bytes in that order (what gguf-hash prints for a whole model; for a safetensors file it is the data buffer). The hash type is written `%-8s` and the columns are two spaces apart, as gguf-hash prints them; the file column is the file's base name; the per-tensor hex is the tensor id above. A file or tensor name containing whitespace or a non-printable character is refused, since `gguf-hash --check` splits a line on whitespace.

## 2. Diff record (implemented)
Per tensor: status in {unchanged, changed, reshaped, added, removed}, the vocabulary `verify` and `show` share. Two tensors of the same dtype and shape are `unchanged` only when their stored bytes are identical and `changed` otherwise; `changed` counts the elements whose bytes differ, so a sign flip of zero, a NaN payload change, or an integer beyond float precision all count. A dtype or shape difference is `reshaped`; when the shapes agree and both dtypes decode, the numeric statistics are still computed, with `changed` counting elements whose decoded values differ (NaN against NaN equal). Numeric statistics, over the changed elements only: `nonfinite_changed` (changed elements whose delta is NaN or infinite), max abs delta and the Frobenius norm of the delta over the finite deltas (null when none is finite), the relative Frobenius norm against the base's finite elements, rows and columns touched (2-D view: first axis by the rest; a 1-D tensor reports rows = changed and no columns; a 0-D tensor neither), and optionally the rank at relative tolerance 1e-2 and the top-1 singular energy over the touched submatrix, omitted when that submatrix exceeds 2^26 elements (the `--rank-cap` default) or holds a non-finite delta. Values are decoded to float64 and deltas are exact (every difference of two values of a 32-bit or narrower type is representable). A tensor whose dtype cannot be decoded (C64) gets the byte-level count only. JSON output never contains NaN or infinity.

## 3. Repository, objects, and deltas (implemented 2026-11-02)

### 3.1 Layout
A repository is any directory containing `.wvc/`:

```
.wvc/config.json               {"format": "wvc-repo/0", "max_delta_depth": 8, "max_tensor_bytes": 17179869184}
.wvc/HEAD                      "ref: refs/heads/main\n"
.wvc/refs/heads/<name>         "<commit id>\n"
.wvc/commits/<commit id>.json  commit record (section 3.4), pretty-printed; the id is over the canonical form
.wvc/manifests/<root>.json     manifest (section 1), exactly as `wvc hash` prints it
.wvc/objects/<aa>/<id>.json    object record: how tensor <id> is stored (section 3.2)
.wvc/payloads/<aa>/<pid>       bytes referenced by records; <pid> = sha256 of the payload bytes
```
`max_tensor_bytes` (written by `init`; default 2^34, 16 GiB; a repository made before it existed gets the default) is the largest tensor, and the largest low-rank factor, an object record may claim; whatever the config says, no tensor or file record may claim more than 2^40 bytes (1 TiB). Ids are lowercase hex SHA-256; `<aa>` is the first two hex characters. Every write is atomic (temporary file in the same directory, then rename). The store is append-only; nothing is rewritten.

### 3.2 Object records and forms
`{"format": "wvc-object/0", "id": <tensor id>, "nbytes": n, "itemsize": k, "form": <form>, ...}` with one of:
- `zstd-planes`: the tensor bytes split into k byte-position planes (plane j holds the bytes at positions congruent to j modulo k), each compressed as one zstd frame (level 3), frames concatenated. Fields: `payload`, `plane_sizes` (frame lengths in plane order). Decode: split by `plane_sizes`, decompress, interleave.
- `delta-xor-planes`: as `zstd-planes`, applied to XOR(base bytes, tensor bytes). Fields: `base` (tensor id), `payload`, `plane_sizes`. Decode: reconstruct the base, decode the planes, XOR.
- `delta-sparse`: fields `base`, `payload`, `index_size`, `value_size`. The payload is one zstd frame of the changed element indices (uint32 little-endian, ascending, element index = byte offset / k) followed by one zstd frame of the changed elements' raw bytes (k bytes each, in index order). Decode: copy the base, overwrite the listed elements. Eligible when at most 5% of elements differ and every index fits in uint32.
- `delta-lowrank` (specified 2026-11-03; produced only by `wvc merge-adapter`): fields `base`, `base_dtype`, `shape`, `payload`, `rank`, `a_dtype`, `a_shape`, `b_dtype`, `b_shape`, `a_size`, `scale`, `procedure`. The payload holds the raw bytes of the adapter factors A (`a_shape` = [rank, in]) followed by B (`b_shape` = [out, rank]) exactly as stored in the adapter file (any safetensors float dtype); `a_size` is A's byte length; `scale` is the decimal text of a Python float (for example `2.0`); `procedure` is `lowrank-merge/0`. Reconstruction under `lowrank-merge/0`: decode the base tensor W (shape [out, in]), A, and B to float64; accumulate D = sum over k in increasing order of outer(B[:, k], A[k, :]) in float64 with numpy elementwise operations (no BLAS matrix product, so the result is identical across machines); W' = W + scale * D in float64; cast to float32 with round-to-nearest-even, then to the base dtype (bf16 by the round-to-nearest-even bit trick; f16 and f32 by numpy casts); the bytes must hash to the object id, which is checked on write and on read. A merge produced by any other arithmetic is stored as an XOR or sparse delta instead.

Every object record also carries `depth`: 0 for a full object, and the base's depth plus one for a delta; readers require exactly the keys the form defines. zstd frames are written at level 3 with the content size in the frame header and no checksum; `index_size` and `value_size` are compressed frame lengths. Every decode verifies `sha256(bytes) == id` and raises on mismatch. Delta chains follow `base` recursively, each level's depth must equal its base's plus one, and readers stop at the smaller of the repository's `max_delta_depth` and 64; `commit` stores a full `zstd-planes` object when the chain would exceed `max_delta_depth`.

Encoding choice at commit time, for each tensor not already in the store: if the parent manifest holds a tensor of the same name, dtype, and shape, the candidates are `delta-sparse` (when eligible) and `delta-xor-planes`; the smaller payload wins, and a delta is kept only when its payload is strictly smaller than the `zstd-planes` payload of the tensor itself; ties keep the earlier candidate in the order full, XOR, sparse. [E002](../experiments/E002-storage-measurement.md) measured these encodings: deltas win by 2x to about 2,000x on structured revisions and by about 20% on dense ones.

### 3.3 File layout records (byte-exact checkout)
A commit records, per source file: `name`, `header` (a payload holding the file's first 8 + N bytes, the size field and the JSON header, verbatim), `tensors` (tensor ids in data-buffer order), `sha256` and `nbytes` of the whole file. Checkout writes the header bytes followed by the tensors in that order and verifies the file hash, so a checkout reproduces the original shard files byte-for-byte; safetensors guarantees the buffer has no holes, so this concatenation is the file.

### 3.3a Extras: the non-tensor files of a checkpoint (designed 2026-11-03; milestone M6)
A checkpoint directory usually holds files a loader needs besides the weights: `config.json`, `generation_config.json`, the tokenizer files, a chat template, a preprocessor config, the shard index `model.safetensors.index.json`, a licence, a model card. `commit` records each top-level file of the directory that is not a `.safetensors` shard, is not a dot file, has a plain portable name (the rules of 3.6, minus the `.safetensors` suffix), is at most 64 MiB, and has an allowed extension or name: `.json`, `.txt`, `.jinja`, `.model`, `.tiktoken`, `.md`, `.yaml`, `.yml`, or a dot-free name starting with `LICENSE`, `LICENCE`, or `NOTICE` (so `LICENSE-MIT` qualifies by prefix, `LICENSE.txt` by suffix, and `LICENSE.py` never). A symbolic link is followed only when its fully resolved target is a regular file inside the resolved checkpoint directory or, for a Hugging Face cache snapshot `<repo>/snapshots/<sha>/` (whose files link to `../../blobs/<hash>`), inside that entry's `<repo>/blobs/`; any other link is skipped and reported as `symlink outside the checkpoint`, so an unpacked archive's `tokenizer.json -> ~/.ssh/id_ed25519` is never stored or pushed (fixed 2026-11-03, second-pass review H2). Extras whose names differ only by case, or collide with a shard's name after NFC normalisation and case folding, refuse the commit, as shards do; dot files are reported as skipped. Each is stored verbatim as one payload (its id is the SHA-256 of the file, so identical files dedup across revisions) and listed in the commit record as `"extras": [{"name", "payload", "nbytes"}, ...]` sorted by name; the total of extras is at most 256 MiB. Files that match none of this (other weight formats such as `.bin`, `.pt`, `.pth`, `.gguf`, code such as `.py`, images, nested directories) are not recorded; `commit` prints their names on stderr as skipped, and `--no-extras` records none. A single `.safetensors` file has no directory of extras, so its commit carries the parent's extras records forward unchanged (same names, payloads, and byte counts, each payload checked to be stored at its size) and `commit` prints `extras: N files carried from the parent, B bytes`; with `--no-extras` it records none. Whenever the parent records extras and the new commit records none (`--no-extras`, or a directory without extras), `commit` says so in one stderr line, `extras: the parent recorded N; this commit records none`, followed by ` (--no-extras)` when that flag was given (fixed 2026-11-03, second-pass review C-M4). Extras never enter the manifest, so identity stays tensors-only; the "nothing changed" rule compares extras as well as the manifest and the file records. `checkout` writes extras by the same all-or-nothing scheme as shards, after verifying each payload's hash and re-applying the name and extension rules, so a received repository can never make a checkout write a code file type (such as `.py`) or an unlisted file type. The rules judge file types, not contents, so no extra is a code file type but some risk remains: a `.jinja` chat template is a program in a template language that a loader runs, and an `auto_map` entry in a config such as `tokenizer_config.json` can point a loader at remote code when the user opts in to it; wvc stores and writes extras verbatim and does not inspect them (wording fixed 2026-11-03, second-pass review C-L3). `show` lists them; `fsck` checks them; `push` and `pull` transfer them.

### 3.4 Commit record
```
{"format": "wvc-commit/0", "manifest": <root>, "parents": [<commit id>, ...],
 "operation": {"kind": <vocabulary>, ...}, "message": str, "author": str,
 "time": "YYYY-MM-DDTHH:MM:SSZ",
 "files": [{"name", "header", "tensors": [<id>, ...], "sha256", "nbytes"}, ...],
 "extras": [{"name", "payload", "nbytes"}, ...]}
```
`extras` may be absent (older commits) or empty.
The commit id is the SHA-256 of the canonical form (3.5). Parents are commit ids (an earlier draft said manifest roots). Operation vocabulary: `pretrain-checkpoint`, `finetune`, `adapter-merge`, `model-merge`, `quantize`, `convert`, `direct-edit`, `prune`, `distill`, `unknown`; extra keys are allowed and preserved; v0 validates only `kind`.

### 3.5 Canonical JSON
UTF-8; keys sorted by Unicode code point; separators `,` and `:` with no whitespace; strings escaped as JSON requires and nothing more (`"`, `\`, and control characters below U+0020 as `\n`, `\t`, or `\uXXXX`; every other character, including U+2028, written raw); no floats in hashed records (sizes are integers, times and scales are strings). Files on disk may be pretty-printed; ids are always computed over the canonical form.

### 3.6 Commands (implemented)
```
wvc init [DIR]
wvc commit CHECKPOINT -m MSG [--op KIND] [--parent REF] [--branch NAME] [--author NAME] [--source SPEC] [--no-extras] [--repo DIR]
wvc log [--repo DIR] [-n N]
wvc show REF [--repo DIR] [--json]
wvc checkout REF --out DIR [--repo DIR] [--force [--overwrite NAME]...]
```
`CHECKPOINT` is a `.safetensors` file or a directory of shards (top-level files ending in `.safetensors`, dot files skipped). File names recorded by a commit must match `[A-Za-z0-9][A-Za-z0-9._-]*\.safetensors`, be at most 200 bytes, not be a Windows reserved device name, not end in a dot or space, and not collide with another record after NFC normalisation and case folding. `commit` refuses files whose tensors do not tile the data buffer exactly (`hash`, `verify`, and `diff` accept them). `--parent` defaults to HEAD (the first commit has no parent); a parent other than the branch head requires `--branch NAME`, which creates NAME at the new commit and points HEAD at it. The author is `--author` or the `WVC_AUTHOR` environment variable; there is no silent default. `REF` is `HEAD`, a full 64-hex commit id (tried first), a branch name, or a commit id prefix of at least 7 hex characters (uppercase accepted); a name that is both a branch and a commit prefix is an error, a full 64-hex id never resolves through a branch, and branch names that look like hex prefixes, end in `.lock`, or differ from an existing branch only by case are refused. `commit` prints: tensors total, reused by hash, stored full, stored as delta by kind, and bytes written. `show` prints the record and counts of tensors changed, unchanged, added, and removed (the `diff` order) against the first parent, from the manifests alone. `commit` refuses a checkpoint as "nothing changed" only when both its manifest root and its file layout records (names, header payloads, file hashes) equal the parent's; a metadata-only or re-sharded revision is therefore a commit with the same root. `put_commit`, `show`, and `checkout` rebuild the manifest from the file records' header payloads and tensor ids and require it to equal the stored manifest, so a commit's files can never disagree with its manifest; `checkout` writes every file as a temporary, verifies all of them, then renames all, prints the verified manifest root, and refuses a non-empty directory unless `--force`. The all-or-nothing scheme covers the renames too: every target name must be absent or a regular file (a symbolic link, a directory, or anything else refuses the checkout, checked before the first write and again before the first rename); each existing target is first moved aside to a `.wvc-<uuid>.tmp` name in the same directory, then every temporary is renamed into place, and if any of these renames fails the new files are removed, the moved-aside files put back, and the error says the directory was restored (or names where a previous file is left if putting it back failed too). The moved-aside files are deleted after the last rename. `checkout` marks each file that replaced an existing one as `replaced` and the summary line counts them. What `--force` may replace (fixed 2026-11-03, second-pass review S-M2): an existing file at a shard name, always, since checkout manages shards; an existing file at an extras name only when its bytes hash to a payload the store holds and some stored commit lists as an extra, that is, an earlier checkout of this store wrote it, or when it is named by `--overwrite NAME` (repeatable; a name the commit does not record is refused). Any other existing file at an extras name refuses the checkout before anything is written, naming the files and `--overwrite NAME`, so a hostile store's `package.json`, `requirements.txt`, or `docker-compose.yml` extra cannot replace a project's own; a file that appears at an extras name after this check refuses the renames. The check hashes each such file (one larger than an extra may be counts as foreign without hashing), looks the hash up among the stored payloads, and only then reads every stored commit once; a commit that cannot be read vouches for nothing.

Durability and trust: every write is fsynced before its rename and the directory after it; the branch ref is updated under an `O_EXCL` lock file with a compare-and-set on the parent; existing payloads are re-hashed before reuse and replaced when wrong, and a damaged commit file under its own id is replaced on the next put; a received object deeper than the local depth cap is refused at pull; symlinks inside `.wvc`, non-regular files, and oversized records are refused; an object record that claims more than the tensor limit (`max_tensor_bytes`, at most 1 TiB) is refused when stored, when read, and by `fsck`, before anything of its size is allocated, a checkout first checks that its output has free space for every file and extra, and running out of memory is reported as an error (`fsck` reports it against the object); a discovered repository owned by another user is refused unless named with `--repo`; error messages never echo file contents. Decode on reuse: `commit` reuses a stored object (record readable, its `nbytes` the tensor's, its payload at the implied size) only after decoding it through its delta chain back to the tensor id, and `pull` decodes every received object the same way before writing its record; a stored object that fails is replaced by the tensor stored in full under the same id, and a received one stops the pull. An empty marker `.wvc/verified/<aa>/<id>`, written atomically after this store decoded an object (on reuse, at pull, or in `fsck`) or encoded it from the tensor's bytes, lets reuse skip that decode; markers are local hints that push and pull never transfer and `fsck` ignores in its layout check, all are removed when a stored record or payload is replaced, and they never relax what `checkout` or `fsck` verify. On Windows, which has no `O_NOFOLLOW`, store reads refuse a symbolic link by comparing the opened file with `lstat` of the path after the open; directories are not fsynced; and the owner check does not exist (no user ids). A checkpoint file stays open for the length of its commit, and Windows refuses another process's attempt to replace it meanwhile (that process's rename fails; the commit is unaffected). Runtime dependencies for this section: numpy and zstandard (decision D4 as amended on 2026-11-02).

## 4. Commands beyond M3

### 4.1 `bisect` (designed 2026-11-03; milestone M4)
```
wvc bisect GOOD BAD --test CMD [--repo DIR] [--workdir DIR] [--keep] [--sweep] [--json]
```
Walks first parents from BAD back to GOOD (BAD must descend from GOOD, else an error); the candidates are the commits after GOOD up to and including BAD, oldest first. Each tested commit is checked out into `WORKDIR/<12-character id>` (a temporary directory by default, removed after its test unless `--keep`). CMD runs through the platform shell (`sh` on POSIX, `cmd.exe` on Windows) with the environment variables `WVC_CHECKOUT` (the directory) and `WVC_COMMIT` (the id) and with the checkout directory, quoted for that shell, appended as its last argument (`sh`: single-quoted as by `shlex.quote`; `cmd.exe`: always in double quotes, with trailing backslashes doubled). On Windows a WORKDIR whose path holds `"`, `%`, `!`, or a line break is refused before any checkout, since inside double quotes `cmd.exe` still expands `%` (and `!` when delayed expansion is on) and has no escape for `"`; exit 0 means good, exit 1 means bad, any other exit aborts the bisect. Binary search assumes one good-to-bad transition and reports the first bad commit, every commit tested with its result and seconds, and the number of tests; when every candidate is good it says so. `--sweep` tests every candidate in order instead, reports every result and the first bad commit, and flags a non-monotone curve (a bad commit followed by a good one), which is how the binary-search assumption is validated. `--json` prints the same as JSON.

### 4.2 Implemented and proposed
Implemented beyond M3: `bisect` (4.1), `merge-adapter` (5.3), `remote`, `push`, `pull`, `clone`, `card` (5.1 and 5.2), and `fsck` (every payload, object, manifest, commit, and ref re-verified; `--no-decode` skips rebuilding tensors). Proposed:
`hash`, `diff`, `verify <ckpt> <manifest>`, `init`, `commit <ckpt> --op ... --parent ...`, `log`, `show`, `checkout <commit> --out <dir>`, `bisect --test <cmd>`, `remote add` (directory, s3://, hf://, oci://), `push`, `pull`, `sign`, `attest`.

`verify` is implemented: it hashes the stored bytes of every checkpoint tensor (nothing is decoded), compares each with its manifest entry, and recomputes the root. Per-tensor status: `ok` (same dtype, shape, and sha256), `mismatch` (same dtype and shape, different sha256), `reshaped` (dtype or shape differ), `missing` (in the manifest only), `extra` (in the checkpoint only). Exit code 0 when every tensor is `ok` and the root matches, 1 otherwise, 2 on an unreadable checkpoint or a malformed manifest.

## 5. Interoperability (designed 2026-11-03; milestone M5)

### 5.1 Sources and model cards (M5a)
`wvc commit ... --source SPEC` records where a checkpoint came from in the commit record's `source` field: `hf:REPO_ID@REVISION` gives `{"kind": "hf", "repo": REPO_ID, "revision": REVISION}` (revision `main` when omitted); any other text gives `{"kind": "path", "value": SPEC}`. `wvc card REF [--manifest-out PATH]` prints model-card YAML front matter: `base_model` is the Hub repo of the nearest commit on the first-parent chain, including REF itself when it has no parent, whose source is `hf`; `tags` are `wvc` and `wvc:op:<kind>`; a comment block carries the manifest root and the commit id. With `--manifest-out`, the manifest JSON (what `wvc hash` prints) is also written to PATH for publishing as a sidecar file, conventionally `wvc-manifest.json`.

### 5.2 Remotes (M5a)
A remote is another wvc store reachable through a transport. `wvc remote add NAME URL` stores it in `config.json` under `remotes` as `{NAME: {"url": URL}}`; `wvc remote list` prints them. URL forms: a directory path (transport `dir`, created on push when missing); `hf://REPO_ID[@REVISION]` (transport `hf`: a Hub model repository holding the store's files under a top-level `wvc/` directory; needs the optional dependency `huggingface_hub`, installed as `wvc[hf]`, and a token for push). The transport interface is `exists(relpath)`, `read(relpath, limit, size) -> bytes`, `write(relpath, data)`, and `list(prefix)`, over the store's own relative paths (`payloads/aa/pid`, `objects/aa/id.json`, `manifests/root.json`, `commits/id.json`, `refs/heads/name`).

`wvc push [REMOTE] [BRANCH]` (defaults `origin` and the current branch): the commits reachable from the local branch head through all parents that the remote lacks are transferred, each with its manifest, header payloads, and the object records and payloads of its tensors including every base of a delta chain, in the order payloads, objects (bases before deltas), manifest, commit; then the remote ref is set when it is absent or an ancestor of the pushed head (fast-forward), and refused otherwise. `wvc pull [REMOTE] [BRANCH]` is the reverse into the local store, hashing every received payload and validating every record before anything referring to it is written, and fast-forwarding the local branch (refused when the histories diverge). Pull reads every remote file under a bound known before the read: an object or extra payload must have exactly the size its record implies, and a header payload, object record, commit record, manifest, or ref must fit the store's own limits; a directory remote's file must be a regular file, not a symbolic link, FIFO, or device, and a Hub file's cached size is checked before it is read. Writes to a directory remote are durable like local ones (section 3.6): a `.wvc-<uuid>.tmp` temporary, fsync, rename, directory fsync. `wvc clone URL DIR` is init, `remote add origin URL`, and pull.

### 5.3 PEFT adapters (M5b)
`wvc merge-adapter BASE_REF ADAPTER_DIR --out DIR -m MSG [--repo DIR]` reads `adapter_config.json` (peft_type `LORA` only; refuses `use_dora`, `fan_in_fan_out`, `rank_pattern`, `alpha_pattern`, non-empty `modules_to_save`, and `layers_pattern` or `layers_to_transform`; scale is `lora_alpha / r`, or `lora_alpha / sqrt(r)` when `use_rslora`) and `adapter_model.safetensors`; maps each pair `base_model.model.<path>.lora_A[.<name>].weight` and `...lora_B[.<name>].weight` to the base tensor `<path>.weight`, which must exist in BASE_REF's manifest with shape [out, in] while A is [r, in] and B is [out, r]; checks out BASE_REF into DIR; overwrites each target tensor's byte range in the checked-out files with the merged tensor computed by `lowrank-merge/0` (so the files keep the base's shard layout and headers); and commits DIR with operation kind `adapter-merge`, storing each target as a `delta-lowrank` object against the base tensor (decoded and verified immediately), with everything else reused by hash. The commit's `operation` carries `{"kind": "adapter-merge", "adapter": {"peft_type": "LORA", "r": ..., "lora_alpha": ..., "scale": ..., "target_modules": [...], "tensors_root": <manifest root of the adapter file>}}`.

### 5.4 Still proposed
Reading GGUF; accepting gguf-hash manifest lines in `verify`; CycloneDX ML-BOM component hashes; a Sigstore signature over the manifest; a proposed `base_model_relation: edit` on the Hub.

### 5.5 Hub checkpoints (implemented 2026-11-03)
`hash`, `diff`, and `verify` accept `hf:REPO_ID[@REVISION]` in place of a path (revision `main` when omitted; needs `wvc[hf]`). The repository is described once through `model_info` with `files_metadata`: the revision is pinned to the commit sha it resolves to, and the top-level, non-hidden `*.safetensors` files are listed with their size and LFS SHA-256 (the Hub's `lfs.oid`); a file the Hub stores as a plain blob has no SHA-256 and is always fetched. Files are fetched with `hf_hub_download` at that sha into the Hub cache. A diff of two Hub repositories skips every shard whose name, size, and SHA-256 agree on both sides and reports its tensors `unchanged` from the header alone, read with two range requests (the size field, then the header; none for an empty header, since `bytes=8-7` is not a valid range) and parsed by the same reader as a local file, bounded by the listed file size. A range request is streamed with a 30-second connect and read timeout and asks for an identity encoding; a status other than 206 (a 200 means the server ignored the range), a `Content-Length` other than the requested length, or an encoded body is refused before the body is read, and a body is refused at the first read that brings it past the requested length; the skipped headers are read and checked before any download, and a tensor name present in a skipped shard and in any other shard on either side is refused, as a local reader refuses a duplicate. A fetched file whose size differs from the listing is refused. `hash` and `verify` print the pinned commit to stderr, and `verify --json` carries the `hf` record. In the JSON record a Hub side is `{"hf": {"repo", "revision", "sha"}, "root": ..., "files": {"skipped": [{"name", "nbytes", "sha256"}], "fetched": [...]}}` (the `files` key only for a diff of two Hub repositories); `root` is null when a shard was skipped, because its tensors were never hashed. The text output starts with two lines naming the pinned commits and the shard counts.

Supported clients: `huggingface_hub` 1.x and 2.x (`wvc[hf]` declares `huggingface_hub>=1`). Hub checkpoints and `hf://` remotes rely on the httpx-based client those lines share: `errors.HTTPError` is the base of its HTTP and network errors, and `utils.get_session()` returns a client with `stream(method, url, headers=, timeout=)`. The requests-based 0.x line has neither (its `errors.HTTPError` is `requests.HTTPError`, which excludes connection errors and timeouts, and its session has no `stream` method). CI exercises only the locked version (2.4.0 when this was written); other versions are not tested there.

## 7. Test vectors
`spec/vectors/v0/` holds two small checkpoints (`a.safetensors`, `b.safetensors`), their manifests, the record `wvc diff --rank --json --all` prints for them (`diff.json`, with paths reduced to basenames), and the deterministic generator `make_vectors.py`; `tests/test_vectors.py` checks this implementation against them. A conforming implementation reproduces both manifests exactly (same keys, tensors sorted by name, same root) and, in the diff, the statuses, element counts, rows and columns touched, and rank exactly. The floating statistics (`max_abs_delta`, `delta_norm`, `rel_delta_norm`, `top1_energy`) must agree within a relative tolerance of 1e-6; see `spec/vectors/v0/README.md`.
